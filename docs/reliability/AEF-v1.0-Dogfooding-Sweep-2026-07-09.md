# AEF v1.0 — Reliability Dogfooding Sweep (2026-07-09)

Autonomous, non-simulated reliability hardening pass over the whole platform (all channels, all capabilities) following GA-3's own precedent: real requests through the real built binaries (`AefPlatform.Host.dll`, `AefPlatform.Cli.dll`), against the real external `C:\POC\Ferret` repository and against `aef-platform` itself. Not scoped to a single Epic/Capability — a full-surface sweep across REST, CLI, Runtime lifecycle, sessions, concurrency, and configuration.

**Baseline**: 471/471 tests passing (matches GA-3's own report) before this sweep began. **Result**: 480/480 passing after — 3 real defects found and fixed, each with regression coverage; one architectural observation logged, not fixed (see below).

## Defects Found and Fixed

1. **Runtime — unhandled exception when a Technology-Profile-selected verification command isn't installed** (`src/Runtime/DomainContent/DeliveryExecution/DeliveryValidationBehavior.cs`). Live-reproduced: `POST /api/v1/execution` with `{"userRequest":"Validate the build","payload":{"RepositoryName":"Ferret","RepositoryRoot":"C:/POC/Ferret"}}` against the real Ferret repository returned an unhandled `500` (REST) because Ferret's detected stack selects `npm` as its validation command, and `npm` is not installed on this host — `ProcessVerificationRunner.Run`'s own deliberate `InvalidOperationException` (for exactly this case, per its own code comment) was never caught anywhere up the call chain. `DeliveryValidationBehavior.Execute` already escalates gracefully when no command can be constructed at all (`ValidationOutcome.Escalated`); it had no equivalent handling for "a command was constructed but can't be run on this host" (missing binary, or a hang past the 10-minute timeout). Fixed by catching `InvalidOperationException`/`TimeoutException` around the runner call and converting to the same `ValidationOutcome.Escalated` path — consistent with the class's own CEI-DEL-07 "halt and report honestly, never fabricate" discipline. Verified live post-fix on both REST (now `200`, `status: Failed`, honest diagnostic) and CLI (exit `1`, same diagnostic). Regression: `DeliveryValidationBehaviorTests.VerificationCommandNotInstalled_Escalates_NeverThrows` (real `ProcessVerificationRunner`, real nonexistent command), `VerificationCommandTimesOut_Escalates_NeverThrows` (stub).

2. **Adapters.Cli — `--output` accepts any value silently** (`src/Adapters.Cli/CliExecuteArgumentsValidator.cs`, `src/Cli/Program.cs`). Neither `execute` nor `capabilities` validated `--output`; any unrecognized value (typos, `xml`, or case variants like `JSON`) silently fell back to text formatting with no error — a scripting caller relying on JSON output could silently get text instead. Fixed by rejecting anything other than exactly `text`/`json` with a usage error (exit `64`), matching the validation already applied to `--user-request`/`--project-profile-id`/`--payload-json`. Regression: `CliExecuteArgumentsValidatorTests.Validate_InvalidOutputValue_ReturnsError` (4 cases: `xml`, `JSON`, `Text`, empty), `ExecuteCommandTests.Execute_InvalidOutputValue_ExitsWithUsageError`, `Execute_OutputValueWrongCase_ExitsWithUsageError`, `CapabilitiesCommandTests.Capabilities_InvalidOutputValue_ExitsWithUsageError`.

3. **Test infrastructure — flaky temp-directory cleanup under full-suite parallel runs** (`tests/Host.Tests/RepositoryEngineeringHostIntegrationTests.cs`). `Execute_PlanRequest_AgainstTheRealBootedHost_DispatchesToEngineeringPlanning` failed once during a full-solution `dotnet test` run (not reproducible running `Host.Tests` alone, 3/3 clean) with `IOException: The process cannot access the file '...' because it is being used by another process` while deleting its temp git-repository fixture — a transient Windows file-lock race on a just-created directory, not a production defect. Fixed with a short bounded retry (5 attempts, linear backoff) around `Directory.Delete`, the standard mitigation for this class of Windows flake. Confirmed clean across 3 subsequent full-suite runs post-fix. Not applied speculatively to the ~8 other test files sharing the same delete-temp-repo pattern — no failure was observed there; flagged below for awareness, not fixed without evidence.

## Documentation Fixed

**CLI Adapter Reference's "Session persistence" claim was false** (`docs/cli/cli-adapter-reference.md`). The doc said `--session-id` lets a caller "continue a multi-turn conversation across separate invocations." Verified live: no `execute` invocation, in any status (`Completed`/`Failed`/`NeedsClarification`), ever returns a non-null `sessionId` — the CLI has no `sessions` command and never calls `IAgentExecutionInterface.StartSession` (confirmed: no reference to `StartSession` anywhere in `src/Adapters.Cli` or `src/Cli`). Passing any `--session-id` (fabricated or otherwise) always fails with `Unknown session.` — already covered by the pre-existing `ExecuteCommandTests.Execute_UnknownSessionId_ExitsOne`, so the *behavior* was already correctly tested; only the *documentation* was wrong. Even a hypothetical future `sessions` command wouldn't fully deliver what the doc promised, since each CLI invocation is its own process with its own empty `InMemorySessionStore`, entirely disconnected from the REST Host's own long-lived one — cross-process session continuity isn't just missing, it's architecturally unavailable to a one-shot CLI as currently composed. Doc corrected to state this plainly as a known limitation rather than an aspirational feature.

## Observation Logged, Not Fixed (needs a product decision, not a code fix)

**`AgentExecutionService`'s "empty ProjectProfileId defers to the session's stored default" fallback is unreachable from both shipped channels.** `AgentExecutionService.Execute`'s own code comment describes this fallback; both `RestExecutionRequestValidator` and `CliExecuteArgumentsValidator` unconditionally reject an empty `ProjectProfileId` before any session lookup happens, in both documented, tested behavior. This isn't a bug — nothing behaves incorrectly, and both adapters' own docs already state `ProjectProfileId` is always required — but the fallback logic is dead from a caller's perspective. Left as-is: enabling it would be a behavior change to two adapters' validation contracts (a product decision on whether the fallback should actually be exposed), not a localized correctness repair, and out of scope for this hardening pass.

## Coverage Confirmed, No Defects Found

- REST malformed-request matrix (empty/missing/wrong-typed fields, malformed JSON, non-JSON content-type, unknown session, oversized payload >1MB, wrong HTTP verbs, unknown routes) — all match documented status codes exactly.
- `PayloadNormalization`'s handling of non-string `JsonElement` kinds (array, nested object, bool, null) as `RepositoryName`/`RepositoryRoot` — degrades honestly to "no repository context supplied," never crashes.
- Concurrency: 100 concurrent REST requests on one shared session (up from GA-3's own 20-request test) — 100 unique `requestId`s, zero corruption. 50 concurrent session creations — 50 unique `sessionId`s. 30 interleaved concurrent requests across two distinct sessions — zero cross-session contamination.
- Long-running: 300 sequential REST requests — zero failures, stable process memory (~92MB, no growth signal).
- Host crash/restart recovery — clean: process dies, restarts healthy, old sessions correctly gone (already-documented limitation, no persistence promised).
- Configuration: `ContentRootPath` pinning holds launching the CLI from arbitrary working directories; `RestAdapter__Port` environment-variable override works as documented.
- REST/CLI parity — byte-for-byte identical JSON shape and content for identical requests against the real Ferret repository, matching GA-3's own dogfooding precedent.
- CLI argument quoting (embedded double quotes in `--payload-json`, Unicode in `--user-request`) — correct, confirms GA-3's `ArgumentList`-based fixture fix holds.

## Stopping Rationale

Stopped per the mission's own criterion: additional probing (AI-provider-backed skills with no configured API key, Kestrel port-conflict startup behavior) either required infrastructure not available in this environment (a real OpenAI key) or reproduced well-understood, non-AEF-specific framework behavior (Kestrel's own `AddressInUseException` on a bound port) rather than a defect in this platform's own code. No fabricated findings; both were reviewed and are noted here for the record, not escalated.
